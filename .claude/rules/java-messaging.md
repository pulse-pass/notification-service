# Messaging

- **NTF-186** An unmapped error, which should not happen, is not handled and is never discarded: it propagates, the message goes to the retry topic `notification_event_retry` and is tried again every `app.notification-event.retry.delay` (default 60000 ms) for up to 7 days, without blocking the other messages of the partition; an expected error is mapped and handled in the code with a `catch`, without rethrowing (e.g. a refusal of the e-mail provider, status 400 or 422: the attempt is saved and the e-mail is `FAILED`); a send error of the provider (any other status, no body, unreachable) is retried only up to 5 attempts of the e-mail message (NTF-204). There is no DLQ.
- **NTF-092** Every message has the envelope `event_type`, `event_key` and `event_data`, in snake_case JSON; the envelope `event_type` is the enum `NotificationEventMessageTypeEnum` (the action on the entity, `NOTIFICATION_EVENT_CREATION` the only one), never the type of the notification, and `event_key` is the `notification_event_key`, with the same value as `event_data.notification_event_key`, and the partition key of the record.
- **NTF-209** The consumer does not validate `event_data` against the envelope and the service does not validate the envelope `event_key`: the equality between `event_key` and `event_data.notification_event_key` is a producer contract, never checked by the consumer.
- **NTF-093** `event_data` carries `notification_event_key`, `notification_event_type` (the type of the notification, e.g. `ORGANIZER_REJECTED`), `person_key` (optional, null for a receiver without account), `origin`, `origin_key`, `receiver_contact` and one block per channel; today the only block is `email`, with `variables`. `notification_event_key` and `notification_event_type` are required, and `ProcessNotificationEventDTO` is built only from the `event_data` (`EventData.toDTO()`), never from the envelope.
- **NTF-094** `receiver_contact` is one object per person with all of that person's contacts: `name` and `email` now, and a new channel adds its field there (`phone_number`), never a second receiver.
- **NTF-095** A new channel arrives as another block next to `email` (e.g. `sms`), and the consumer generates one message for each block present.
- **NTF-096** The subject, template and required variables of each type live in the `notification_event_type` row (`email_subject`, `email_template`, `email_variables` separated by commas); there is no Java enum of type, origin or template, and the consumer looks the type up by the `event_data.notification_event_type` that came in the message.
- **NTF-097** A notification type (`event_data.notification_event_type`) with no row in `notification_event_type` throws `NotificationEventTypeNotFoundException` and the message goes to the retry topic (NTF-186); an envelope `event_type` the consumer does not handle throws `UnsupportedNotificationEventMessageTypeException`, with the same result.
- **NTF-098** An invalid message (broken JSON, a missing required field of the envelope, of `receiver_contact` or of `email`, an unknown `origin`, a variable required by the type that is missing) is an unmapped error: broken JSON and failed validation propagate from the converter, the others throw `InvalidNotificationEventException`, and the message goes to the retry topic (NTF-186).
- **NTF-099** The `event_data` is stored whole in `notification_event.data`, and the data of the send (`recipient_email`, `recipient_name`, `subject`, `template`, `variables`) in `email_message.email_data`, so a new attempt never depends on the Kafka message; the stored `variables` are exactly `event_data.email.variables`, with nothing added by the service (NTF-205).
- **NTF-205** The service never injects variables: everything the template uses, including `recipient_name` (required by every type), comes from the producer in `event_data.email.variables`, and `receiver_contact.name` is only the name of the contact in the `to` field of the send; the required variables of each type are in `email_variables` (NTF-096). Fixed URLs of the fronts (e.g. the backoffice link) are written in the template itself, never in a property or an environment variable.
- **NTF-100** The consumer is a profile of the same application (`notification_event-consumer`, with `spring.main.web-application-type=none`), and its listener starts only when `app.consumers.notification-event` is true, read by the container factory (`setAutoStartup`); a new consumer gets its own profile and property, never a shared one.
- **NTF-101** The consumer name `<service>-<topic>-consumer` is also the Kafka group id.
- **NTF-102** The listener uses `enable.auto.commit=false` with the ack done by the container after the processing, and `auto.offset.reset=earliest`.
- **NTF-103** The consumer locks the event (`notification-event:<notification_event_key>`, TTL 60 s, the key taken from `event_data`) with `Cache.acquireLock` before calling the service and releases it with `Cache.delete` in the `catch` (before rethrowing) and after the `try` on the success path, with no `finally`; if the lock is not obtained it logs a `warn` and throws `NotificationEventLockedException`, because returning would make the container ack the message, and the retry topic delivers it again; the service knows nothing about the lock.
- **NTF-104** Idempotency: the event and its `PENDING` e-mail message are saved with the history in the same transaction (`createEmailMessage`); a repeated key is ignored with an `info` log when the e-mail message is `SENT` or `FAILED` (final states, never resent by itself), and a `PENDING` one goes to a new send attempt.
- **NTF-105** The send is the private method `processEmailMessage` of the service (NTF-044), called by the public flow in the same transaction right after the event is saved (or found): it loads the e-mail message of the event without a lock of its own (NTF-206), ignores it with an `info` log when it is `SENT` or `FAILED` (no commit: the record interceptor rolls back the open transaction) and sends it when `PENDING`, with one branch per result and no mutable variables; every attempt saves an `email_message_attempt` with a single `error_code` (`null` on success, the `getCode()` of the domain exception on failure: `NTF00001`, `NTF00006` or `NTF00007`); it looks up the `SENT` and `FAILED` statuses itself (NTF-045); a success sets the `external_message_key` of the message to the id of the provider and `SENT` with its history, saves the attempt with a `null` `error_code`, and commits; a refusal of the provider (`EmailRefusedException`, a mapped error) sets `FAILED` with its history, commits, with a `warn` log and no rethrow; any other failure of the gateway call, caught by the base `catch (Exception ex)` (NTF-078), saves the attempt with the code of `EmailSendingException` (`NTF00007`), sets `FAILED` with its history, commits and does not rethrow, with no retry.
- **NTF-106** The retry is non-blocking, configured by the `RetryTopicConfiguration` bean of `NotificationEventKafkaConfig` (`RetryTopicConfigurationBuilder` with `includeTopic("notification_event")`), never by annotations on the consumer: `maxAttempts` comes from `app.notification-event.retry.max-attempts` (default 10081: the original attempt plus 10080 retries, 7 days at the default delay of 1 min; after that Spring logs and drops the record; Spring builds one backoff value per attempt, so `Integer.MAX_VALUE` does not fit in memory), the fixed delay from `app.notification-event.retry.delay` (env `NOTIFICATION_EVENT_RETRY_DELAY`, default 60000 ms, fixed to 500 ms by `service-start.sh` in `test` mode, NTF-210), `retryTopicSuffix("_retry")` and `SameIntervalTopicReuseStrategy.SINGLE_TOPIC`, so every attempt reuses the single topic `notification_event_retry`; `doNotConfigureDlt()`; `doNotAutoCreateRetryTopics()`, because the topic is declared as a `NewTopic` (NTF-108). The retry uses the container factory `kafkaListenerContainerFactory` (`listenerFactory`) and the same `consume` method (lock, dispatch and service), so the interceptor, the converter, the validation and `AckMode.RECORD` apply to it too.
- **NTF-107** There is no DLQ (`doNotConfigureDlt()`) and no recovery: nothing changes a status or discards a record while the retries go on; when the last attempt is spent Spring only logs and drops the record, which is why the limit is practically unreachable. `NotificationEventRetryTopicConfig` (`RetryTopicConfigurationSupport` in `infrastructure/kafka`) empties the list of non-blocking fatal exceptions of Spring (`DeserializationException`, `MessageConversionException`, `ConversionException`, `MethodArgumentResolutionException`, `NoSuchMethodException`, `ClassCastException`), so no exception is dropped, and declares the `TaskScheduler` the retry needs to resume the paused partitions. There is no `DefaultErrorHandler` in the factory.
- **NTF-108** The service that owns the entity declares its topics as `NewTopic` beans (1 partition, 1 replica, 7 days of retention): `notification_event` and its retry topic `notification_event_retry`; Spring does not create the retry topic (NTF-106).
- **NTF-202** The number of consumer threads per topic is the constant `CONCURRENCY` (1) of `NotificationEventKafkaConfig`, next to `PARTITIONS` (1), set on the container factory with `setConcurrency`, so the main and the retry listeners get the same value; it never goes above `PARTITIONS`, because a partition has at most one consumer per group and the extra threads stay idle, so raising the parallelism means raising both constants together.
- **NTF-203** The consumer method keeps only `@KafkaListener` with its `id` (the consumer group) and `topics`; every other setting of the consumption (partitions, concurrency, auto startup, converter, interceptor, retry) lives in `NotificationEventKafkaConfig`, and topic names are written in full in its constants (`TOPIC`, `RETRY_TOPIC`), never built from a suffix.
- **NTF-109** The consumer writes `/tmp/notification_event-consumer.ready` when it receives its partitions (a `ConsumerAwareRebalanceListener` set in the container factory, so the main and the retry containers both call it), and the compose healthcheck reads it.
- **NTF-110** The consumer method locks the event, calls the service and releases the lock in the `catch` and after the `try` (NTF-103), but never rolls back: the `OpenEntityManagerInRecordInterceptor` (`RecordInterceptor` in `infrastructure/kafka`) plays the role of the end of the request and rolls back with `unitOfWork.rollback()` when `unitOfWork.isActive()`, in `failure` (before the error handler runs) and in `afterRecord`; it is a property of the container factory, so it also runs for the records of the retry topic.
- **NTF-180** The container reads `String` keys and values (`StringDeserializer`), converts the payload with `StringJacksonJsonMessageConverter` (Jackson 3, snake_case `JsonMapper` of the application) and validates the listener parameter declared as `@Payload @Valid <Message>` with the Bean Validation validator registered in the `KafkaListenerEndpointRegistrar`, so the consumer method receives a message that is already valid.
- **NTF-181** Broken JSON (`MessageConversionException`/`ConversionException`) and a failed validation (`MethodArgumentNotValidException`) are not special: they propagate and the message goes to the retry topic like any other unmapped error (NTF-186).
- **NTF-182** In Spring Kafka the error handling runs before `afterRecord`, so the interceptor also rolls back in `failure`; each new attempt of the same record (from the retry topic) opens a new `EntityManager` and starts clean.
- **NTF-185** After the lock, the consumer dispatches on the envelope `event_type`, the enum `NotificationEventMessageTypeEnum` (`api/messages`, deserialized straight into the record): `if (message.eventType() == NOTIFICATION_EVENT_CREATION)` calls `NotificationEventService.processNotificationEventCreation(message.toDTO())`, a new envelope action becomes another `if` calling its own service method, and the `else` logs a literal `warn` (NTF-086) and throws `UnsupportedNotificationEventMessageTypeException`; the lock is released as in NTF-103.
- **NTF-204** The send of an e-mail message has at most 5 attempts (`MAX_EMAIL_ATTEMPTS` in `NotificationEventService`), counted by the rows of `email_message_attempt` of the message (`countByEmailMessageId`, derived query); when `EmailProviderUnavailableException` is caught, the service saves the attempt in the open transaction and counts: below 5 it commits and rethrows, so the message goes to the retry topic; on reaching 5 it sets `FAILED` with its history, commits, logs a `warn` and does not rethrow, so the message is acked and leaves the queue. Other unmapped errors (database, invalid message, type not found, lock busy) keep the 7-day limit of NTF-106.
- **NTF-206** The consumer flow locks the `notification_event` with `findForUpdateByNotificationEventKey` right after `unitOfWork.begin()` and runs the whole flow (creation of the event and of the e-mail message, send, attempt, status) in that one transaction; the e-mail message is read without a lock of its own because it belongs to the locked event.
